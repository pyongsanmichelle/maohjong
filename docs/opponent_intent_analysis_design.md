# Maohjong 対戦相手の狙い役・待ち牌推定 基本設計書

## 1. 目的

入力済みの公開局面から、上家・対面・下家が狙っていそうな役と待ち牌の候補を、相手別に根拠付きで表示する。

本機能は相手の非公開手牌を復元するものではない。表示する数値は統計的な成立確率ではなく、河、副露、ドラ、巡目、見えている牌、手出し・ツモ切り、リーチ宣言から得られる根拠を一定のルールで比較するための`0`から`100`の確信度スコアとする。候補を断定せず、情報が不足する場合は推定結果を表示しない。

初期実装は外部AI、有料API、通信処理を使わず、端末内の純粋なDartで完結させる。

## 2. 対象範囲

### 2.1 含めるもの

1. ルールベースによる相手別の狙い役候補
2. 34種類の牌から求める相手別の待ち牌候補
3. 手出し・ツモ切り、リーチ宣言牌、副露タイミングを含む公開アクション履歴
4. 候補ごとの確信度、根拠、反証、見込み残数の表示
5. 入力訂正・取り消し後の履歴修正と再分析
6. 既存データに詳細履歴がない場合の互換動作
7. 既存の守備分析で使う現物、筋、壁、ワンチャンス、ドラ、見えている枚数の共通化
8. 同じ入力から常に同じ結果を返す決定的な判定

### 2.2 含めないもの

- 相手の手牌、役、待ちの確定
- 表示スコアを和了確率、放銃率として扱うこと
- 点数、翻数、期待値、押し引きの判断
- ダブルリーチ、オープンリーチなどローカルルールの網羅
- フリテンを含む和了可否の完全判定
- カメラ認識、音声読み上げ
- 外部AI API、クラウド推論、機械学習モデル
- 牌譜を使った統計学習

## 3. 前提と制約

- 相手の非公開手牌が分からないため、特に門前手の役と待ちは不確実性が高い。
- 副露が多い相手ほど役候補を絞りやすい。
- リーチは聴牌の根拠になるが、待ちの形や牌を直接示すものではない。
- 相手の河にある牌はロンできない可能性が高いが、ツモ待ちまで否定しない。
- 手出し・ツモ切りが`unknown`の場合、その情報に依存するルールを適用しない。
- 初期入力や過去局面に時系列情報がない場合、現在の河と副露だけで利用可能な範囲を分析する。
- 入力漏れや誤りがある場合、結果も不正確になる。

画面には常に次を表示する。

> 役・待ち候補は公開情報から求めた推定です。実際の手牌や和了を保証しません。

## 4. 利用者操作

1. 従来どおり親、ドラ表示牌、自分の手牌を設定して対局入力を開始する。
2. 相手の打牌を入力するとき、必要に応じて「手出し」「ツモ切り」「不明」を選ぶ。
3. リーチが宣言された打牌では、打牌確定前に「リーチ宣言牌」を指定する。
4. チー・ポン・カンを登録すると、直前の打牌との関係と発生順が履歴へ記録される。
5. 「相手分析」を開き、上家・対面・下家から対象を選ぶ。
6. 「狙い役」欄で、上位候補、確信度、根拠、反証を確認する。
7. 「待ち牌」欄で、最大3件の候補、見込み残数、待ち形候補、根拠を確認する。
8. 候補をタップまたは長押しし、スコアへ寄与した根拠値の詳細を確認する。
9. 誤入力は従来の取り消し、または履歴編集から訂正する。訂正後は分析結果を再計算する。

## 5. 画面設計

守備分析画面とは入口を共通化できるが、目的の異なる結果を混在させない。分析画面内を「危険牌」「狙い役・待ち」のセグメントで切り替える。

```text
┌────────────────────────────────┐
│ 相手分析                        │
│ [上家] [対面] [下家]            │
│ [危険牌] [狙い役・待ち]          │
│ 推定であり実際の手牌を保証しません │
├────────────────────────────────┤
│ 狙い役                          │
│ 1. 混一色  確信度 68/100  [有力] │
│ 2. 役牌    確信度 52/100  [候補] │
│ [選択した候補の根拠・反証]       │
├────────────────────────────────┤
│ 待ち牌候補                       │
│ [3萬 61/100 残2] [6萬 55/100 残3]│
│ 待ち形候補: 両面・嵌張            │
│ [選択した候補の根拠]             │
└────────────────────────────────┘
```

### 5.1 表示規則

- 確信度は`68%`ではなく`68/100`と表示し、統計的確率との誤認を避ける。
- 確信度に加えて「弱い候補」「候補」「有力」「公開情報から成立確認」の文字を表示する。
- 役候補は最大3件、待ち牌候補は最大3件を初期表示する。
- 同点の場合、役は定義順、牌は`Tile.index`順で並べる。
- 根拠と反証を分け、スコアを上げた情報だけを表示しない。
- 待ち候補には現在の局面で見えていない見込み枚数を表示する。
- 見えている枚数が4枚の牌は待ち候補から除外する。
- 十分な根拠がない場合はカードを空で埋めず、「情報が不足しています」と表示する。
- 色だけに依存せず、段階名と数値を併記する。
- 役や待ちの断定表現である「確定」「絶対」は使わない。ただし、公開牌だけで役の成立条件を満たす場合は「公開情報から成立確認」と表現する。

### 5.2 打牌入力の追加操作

- 相手の河を入力するとき、直前に選んだ入力種別を初期値にしない。毎回`unknown`を初期値とする。
- 簡易入力を維持するため、牌の通常タップは従来どおり`unknown`で即時登録できる。
- 手出し・ツモ切りを記録する場合は、牌の長押しまたは打牌確定後の履歴編集を使う。
- リーチは同じ打牌の属性として登録し、別の牌イベントを作らない。
- リーチ宣言の取り消しは打牌を残したまま属性だけを`false`へ戻せる。

## 6. 公開アクション履歴

### 6.1 RoundActionHistory

局内で観測した公開アクションを発生順に保持する。分析側は河の見た目ではなく、この履歴を優先して使う。

- `actions`: `RoundAction`の不変ビュー
- `nextSequence`: 次に採番する局内連番
- `appendDiscard`: 打牌を追加する
- `appendMeld`: 副露を直前打牌へ関連付けて追加する
- `updateDiscard`: 入力種別やリーチ属性を訂正する
- `removeFrom`: 取り消し対象以降の依存アクションを戻す
- `clearForNextRound`: 次局開始時に履歴を初期化する

履歴の更新は`MatchInputFlow`と`SituationEditor`を通し、Widgetから直接リストを変更しない。

### 6.2 RoundAction

全アクションが共通して持つ値は次のとおり。

- `id`: 訂正と関連付けに使う局内一意ID
- `sequence`: 発生順を表す単調増加整数
- `actor`: 自分、下家、対面、上家

### 6.3 DiscardAction

- `tile`: 打牌
- `river`: 既存`InputTarget`との対応
- `source`: `unknown`、`drawn`、`fromHand`
- `declaresRiichi`: リーチ宣言牌か
- `turn`: 登録時点の巡目
- `visibleInRiver`: 鳴かれた後も履歴を残したまま、河に表示中かを表す

同じ牌が複数捨てられても`id`で区別する。鳴かれた牌は`visibleInRiver=false`にするが、現物、筋、役、待ち推定の履歴からは削除しない。

### 6.4 MeldAction

- `meld`: 既存`Meld`
- `calledDiscardId`: 鳴き元の`DiscardAction.id`。開始時登録では`null`
- `declaredAfterSequence`: 副露が発生した位置
- `origin`: 対局中の鳴きか開始時登録か

既存の`Meld`を複製せず、時系列に必要な関連だけを保持する。

### 6.5 互換性

- 履歴が空でも、既存の河と副露から`unknown`の読み取り専用履歴を組み立てて分析できる。
- 河から鳴かれて消えた牌は、従来どおり`Meld.fromRiver`と`calledTile`から補完する。
- 互換履歴では手出し・ツモ切り、リーチ位置、副露の正確な発生順を推測しない。
- `GameSituation.count(tile)`の対象は従来どおり手牌、河、ドラ、副露とし、履歴を重ねて数えない。

## 7. 分析入力

### 7.1 OpponentAnalysisContext

役推定と待ち推定が共通で使う読み取り専用スナップショットとする。

- `situation`: 既存の`GameSituation`
- `opponent`: 既存の`Opponent`
- `roundWind`: 場風
- `dealer`: 親位置
- `turn`: 現在巡目
- `discardHistory`: 対象相手の打牌履歴
- `meldActions`: 対象相手の副露履歴
- `riichiDiscard`: リーチ宣言牌。未宣言なら`null`
- `visibleCountByTile`: 34種類の見えている枚数
- `remainingCopiesByTile`: `4 - visibleCount`を`0...4`へ丸めた値
- `evidenceSufficiency`: `none`、`low`、`usable`

コンテキスト生成時に同一牌5枚以上などの不正局面を検出し、分析器ごとに重複検証しない。

### 7.2 情報充足度

推定結果を無理に出さないため、次の順で判定する。

- `none`: 対象相手の河、副露、リーチ情報がすべてない。
- `low`: リーチがなく、副露もなく、打牌が8枚未満。
- `usable`: リーチ済み、1組以上の副露がある、または打牌が8枚以上ある。

`none`では役・待ち候補を返さない。`low`では明確な役根拠がある場合だけ弱い役候補を返し、待ち候補は返さない。`usable`でも各候補が最低表示スコアに届かなければ空結果を返す。

## 8. 役推定ドメイン

### 8.1 YakuKind

初期対象は次のとおり。

- `honitsu`: 混一色
- `chinitsu`: 清一色
- `toitoi`: 対々和
- `yakuhai`: 役牌。対象牌を`relatedTiles`に保持する
- `tanyao`: 断么九
- `chanta`: 混全帯么九
- `junchan`: 純全帯么九
- `ittsuu`: 一気通貫
- `sanshokuDoujun`: 三色同順
- `chiitoitsu`: 七対子
- `kokushiMusou`: 国士無双

七対子と国士無双は門前の非公開情報へ強く依存するため、公開情報だけの初期版ではスコア上限を`39`とし、「弱い候補」を超えない。

### 8.2 IntentConfidenceLevel

- `weak`: 30から44
- `candidate`: 45から64
- `likely`: 65から89
- `confirmedByOpenInformation`: 90から100

30未満は表示しない。しきい値はドメイン定数として管理する。

### 8.3 IntentReasonCode

表示文ではなく、少なくとも次の理由コードと根拠値を返す。

- `sameSuitMelds`: 同色の副露数
- `offSuitDiscards`: 対象外の色を捨てた枚数と時期
- `honorsRetainedPattern`: 字牌を序盤に捨てていない傾向
- `tripletMelds`: 刻子・槓子の副露数
- `sequenceMelds`: 順子の副露数
- `yakuhaiMeld`: 公開された三元牌または役風の刻子・槓子
- `allSimpleMelds`: 副露がすべて中張牌
- `terminalHonorMelds`: 么九牌を含む副露数
- `straightComponents`: 一気通貫を構成する公開順子
- `threeColorComponents`: 三色同順を構成する公開順子
- `closedHandRequired`: 副露により候補を否定
- `contradictingMeld`: 役条件と矛盾する副露
- `contradictingDiscardPattern`: 河の傾向が候補を弱める
- `insufficientHiddenInformation`: 非公開情報が多いため上限を適用

`scoreDelta`、`relatedTiles`、`evidenceCount`、`sequenceRange`、`priority`を保持し、UIで根拠と反証へ分ける。

### 8.4 YakuHypothesis

- `yaku`: 役の種類
- `opponent`: 対象相手
- `score`: 0から100の相対確信度
- `level`: 確信度段階
- `positiveReasons`: 肯定根拠
- `negativeReasons`: 反証
- `relatedTiles`: 役牌など役固有の牌

### 8.5 YakuIntentAnalyzer

`OpponentAnalysisContext`を受け取り、役ごとの独立した`YakuIntentRule`を評価する純粋なドメインサービスとする。

- Flutter、表示文、色、通信、時刻、乱数へ依存しない。
- 各ルールは肯定根拠と反証の両方を返す。
- スコアは初期値へ寄与値を加算し`0...100`へ丸める。
- 役同士の排他関係で候補を削除せず、反証とスコアで表現する。
- 公開情報だけで成立確認できる役牌などは、成立条件と対象牌を結果へ残す。

## 9. 待ち牌推定ドメイン

### 9.1 WaitShape

- `ryanmen`: 両面
- `kanchan`: 嵌張
- `penchan`: 辺張
- `shanpon`: 双碰
- `tanki`: 単騎
- `unknown`: 公開情報から形を絞れない

待ち形は断定せず、牌ごとに成立し得る形の候補リストとして保持する。

### 9.2 WaitReasonCode

- `dangerAssessment`: 既存の現物・筋・壁・ワンチャンス評価
- `yakuAlignment`: 上位の役候補と牌種が整合する
- `meldNeighborhood`: 公開順子や刻子の周辺牌
- `riichiDiscardNeighborhood`: リーチ宣言牌前後の手出しから得た弱い根拠
- `remainingCopies`: 見込み残数
- `furitenRisk`: 対象相手の河に同じ牌がある
- `allCopiesVisible`: 4枚見えのため除外
- `weakEvidence`: 候補を絞る情報が少ない

### 9.3 WaitCandidate

- `tile`: 候補牌
- `opponent`: 対象相手
- `score`: 0から100の相対確信度
- `remainingCopies`: 見込み残数
- `possibleShapes`: 待ち形候補
- `reasons`: スコア根拠
- `furitenRisk`: ロン不可の可能性を示す注意値

### 9.4 WaitCandidateAnalyzer

34種類の牌を候補にし、次の順で評価する。

1. `remainingCopies == 0`を候補から除外する。
2. 既存の守備分析を候補牌に対して実行し、現物、筋、壁、ワンチャンス、ドラ、副露傾向の結果を共通利用する。
3. 上位の`YakuHypothesis`と色、么九牌、役牌の整合性を評価する。
4. 公開副露の形と周辺牌から、成立し得る待ち形を列挙する。
5. 手出し・ツモ切りとリーチ宣言牌が入力済みの場合だけ、宣言前後の変化を弱い補助根拠として加える。
6. 相手の河に同じ牌がある場合は`furitenRisk`を付けて大きく減点するが、ツモ待ちを考慮して除外はしない。
7. 根拠のない牌は表示最低スコア未満にする。
8. スコア降順、同点は`Tile.index`順にし、上位3件を返す。

待ち推定は隠れた牌姿を生成しない。両面、嵌張などの形は公開情報と矛盾しない可能性としてのみ表示する。

### 9.5 既存守備分析の再利用

待ち候補用に筋、壁、ワンチャンス、ドラのロジックを複製しない。`DangerAnalyzer`を次の形へ内部リファクタリングする。

```text
DangerAnalyzer.analyze(hand tiles)
        └─ VisibleRiskRules.assess(candidate tiles)

WaitCandidateAnalyzer
        └─ VisibleRiskRules.assess(all remaining tiles)
```

`AnalyzeDangerUseCase`の公開動作、スコア、理由順、既存テストは維持する。共通化は判定材料を再利用するためであり、危険度スコアをそのまま待ちの確率として表示しない。待ち分析側では一つの寄与値として正規化する。

## 10. アプリケーション層

### 10.1 AnalyzeOpponentIntentUseCase

画面からの唯一の分析窓口とする。

1. `OpponentAnalysisContextFactory`で局面と履歴を検証する。
2. `YakuIntentAnalyzer`で役候補を求める。
3. 役候補を`WaitCandidateAnalyzer`へ渡して待ち候補を求める。
4. 情報充足度と警告を含む`OpponentIntentAnalysis`を返す。

### 10.2 OpponentIntentAnalysis

- `opponent`: 対象相手
- `evidenceSufficiency`: 情報充足度
- `yakuHypotheses`: 表示可能な役候補
- `waitCandidates`: 表示可能な待ち候補
- `warnings`: 情報不足、履歴互換、不正確になり得る項目のコード

例外を通常の情報不足に使わない。不正な5枚目など分析不能な局面だけを入力エラーとする。

## 11. プレゼンテーション層

- `OpponentIntentPage`: 相手選択と結果全体
- `YakuHypothesisSection`: 役候補の順位、段階、スコア
- `WaitCandidateSection`: 待ち牌、見込み残数、待ち形候補
- `IntentEvidenceSheet`: 根拠、反証、根拠値の詳細
- `IntentReasonFormatter`: 理由コードを日本語へ変換
- `DiscardMetadataEditor`: 手出し・ツモ切り、リーチ属性の入力・訂正

Formatter以外へ日本語の判定文を埋め込まない。Widgetは分析ルールを持たず、UseCaseの結果を表示する。


依存方向は`presentation -> application -> domain`とし、ドメインからFlutterへ依存しない。

## 13. 更新と取り消し

- 打牌追加時に、河への牌追加と`DiscardAction`追加を同一操作で行う。
- 鳴き確定時に、元の`DiscardAction.visibleInRiver`と`MeldAction`を同一操作で更新する。
- 打牌取り消し時は、対象打牌から派生した副露とメタデータも戻す。
- 手出し・ツモ切り、リーチ属性だけの訂正では牌の残数を変更しない。
- 副露の取り消しでは`MeldAction`を除き、元の打牌を河へ戻して`visibleInRiver=true`にする。
- 次局移行では牌情報と同時に履歴を初期化する。
- すべての変更後、保持済みの分析結果を直接修正せず、UseCaseを再実行する。

## 14. エラーと空状態

- 対象相手の情報がない場合: 「河・副露・リーチ情報を入力してください」
- 情報充足度が低い場合: 「待ちを絞る情報が不足しています」
- 役候補だけある場合: 役候補を表示し、待ち欄は情報不足とする
- 待ち候補の残数がすべて0の場合: 「見えている牌との整合性を確認してください」
- 同一牌が5枚以上ある場合: 分析せず既存の入力修正導線を表示する
- 履歴と河が不整合な場合: 互換履歴へ黙って置換せず、警告コードを返して訂正を促す

## 15. テスト方針

### 15.1 履歴テスト

- 同じ牌の複数打牌をIDと順番で区別できる。
- 手出し、ツモ切り、不明を登録・訂正できる。
- リーチ宣言が対象打牌の属性として保持される。
- 鳴かれた牌が河から消えても打牌履歴に残る。
- 副露が直前打牌と関連付く。
- 打牌、副露、属性訂正の取り消しで依存履歴が整合する。
- 次局移行で履歴が初期化される。
- 履歴がない既存局面から互換履歴を生成できる。
- 履歴を`GameSituation.count`へ重複加算しない。

### 15.2 役推定テスト

- 同色副露と色の偏った河から混一色・清一色候補を区別する。
- 字牌の有無が混一色と清一色の反証になる。
- 刻子・槓子の副露数が対々和候補へ反映される。
- 三元牌と正しい役風の公開刻子だけを役牌の成立確認にする。
- 中張牌だけの副露と河の傾向が断么九へ反映される。
- 么九牌を含む副露から混全帯么九・純全帯么九を区別する。
- 公開順子から一気通貫・三色同順の構成要素を評価する。
- 副露がある場合に七対子・国士無双を候補から除外する。
- 七対子・国士無双の公開情報だけのスコアが39を超えない。
- 肯定根拠と反証が別々に保持される。
- 30未満の候補を表示対象にしない。
- 同じ局面で順位、スコア、理由順が変わらない。

### 15.3 待ち推定テスト

- 34種類から残数0の牌を除外する。
- 見込み残数を既存の見えている牌から正しく求める。
- 既存の現物、筋、壁、ワンチャンス材料を共通ルールから取得する。
- 役候補と整合する牌種だけに対応理由が付く。
- 相手の河に同じ牌がある場合に除外せずフリテン注意と減点を付ける。
- リーチ未入力時に宣言牌周辺ルールを適用しない。
- 手出し・ツモ切り不明時に時系列ルールを適用しない。
- 待ち形を単一形として断定しない。
- 情報不足時に待ち候補を返さない。
- 上位3件、同点時の牌順が決定的である。
- 分析前後で局面と履歴を変更しない。

### 15.4 回帰テスト

- `AnalyzeDangerUseCase`の既存スコア、理由、並び順が変わらない。
- 危険率表示と長押し理由表示が維持される。
- 通常タップによる簡易打牌入力が維持される。
- ツモ前打牌防止、手番遷移、チー・ポン・カンが維持される。
- 取り消し、局終了、次局移行が維持される。
- 牌の4枚制限と見込み残数が維持される。

### 15.5 Widgetテスト

- 上家、対面、下家を切り替えられる。
- 危険牌と狙い役・待ちを切り替えられる。
- 役候補に順位、段階、`n/100`、根拠、反証が表示される。
- 待ち候補に牌、段階、`n/100`、残数、待ち形候補が表示される。
- 候補のタップまたは長押しで理由詳細を確認できる。
- 推定である旨の注意文が常に表示される。
- 情報不足時に候補カードを表示しない。
- 打牌へ手出し・ツモ切り・リーチを追加し、後から訂正できる。
- 訂正後に画面を開き直すと結果が再計算される。

## 16. 実装順序

### Phase 1: 役推定

1. `OpponentAnalysisContext`と情報充足度を追加する。
2. 理由コード、役候補モデル、役ルールを追加する。
3. 既存の河、副露、ドラ、巡目だけで分析するUseCaseを追加する。
4. 相手選択、役候補、根拠・反証を表示する。

### Phase 2: 待ち牌推定

1. 既存`DangerAnalyzer`から再利用可能な`VisibleRiskRules`を抽出する。
2. 既存守備分析の回帰テストを固定する。
3. 34種類の候補、見込み残数、役整合性、待ち形候補を評価する。
4. 最大3件の候補と情報不足表示を追加する。

### Phase 3: 履歴情報による精度改善

1. `RoundActionHistory`、`DiscardAction`、`MeldAction`を追加する。
2. 通常タップを維持したまま、手出し・ツモ切り・リーチ入力を追加する。
3. 副露タイミング、取り消し、次局移行と履歴を統合する。
4. 時系列ルールを役推定・待ち推定へ追加する。
5. 既存局面向けの互換履歴を追加する。

各Phaseは個別にテスト可能な状態で完了させる。Phase 3の入力がない状態でもPhase 1・2は動作する。
